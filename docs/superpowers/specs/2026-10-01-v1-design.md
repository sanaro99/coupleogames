# CoupleOGames V1 design

Build the approved private, phone-first game table for exactly two partner identities. A single first-visit form names both partners. Names and access keys are server-only environment defaults; user edits and records live in a private SQLite database. Neither belongs in source control. Each seat has its own private invitation key, exchanged for an HTTP-only session cookie. The owner provisions these separately from an ignored invitation file. Authenticated seats can share only the ordinary table address, never retrieve the other seat’s credential. There is no public registration or room discovery.

## Experience
Warm cream background, ink typography, mint and peach partner colors, original rounded black-cat host, tangible game tiles. Portrait phones are the primary layout; laptop layouts expand deliberately. Normal HTML carries text and touch/keyboard controls. The cat and a shallow Clue Quest tabletop use Three.js with fixed cameras; 2D versions preserve all functionality. Effects are brief and event-driven, respect reduced motion, stop when hidden, and are independently switchable. The cat introduces games, reacts only to public outcomes, sleeps while waiting, and never blocks controls.

## Four games
- Doodle Duo: cooperative, six alternating drawing rounds, 60 seconds each. Drawer alone receives a prompt; partner guesses. Correct guess or timeout reveals the answer. Three correct rounds completes the challenge. Both acknowledge reveals before advancing.
- Know Me Better: competitive, six alternating subject rounds; each gets three chances to guess. Subject privately commits one of four answers, partner guesses, both reveal together. Most correct guesses wins; equal scores draw. Questions are playful preferences, never relationship judgments.
- In Sync: cooperative, six simultaneous free-text rounds. Each commits once, reveal only after both submit. Case, accents, spacing and punctuation normalized; same normalized phrase matches. Three matches completes the challenge; track best streak.
- Clue Quest: original cooperative clue board with 12 shuffled word tiles, six targets (three per partner), two traps and four neutral tiles. Each partner sees only their own target labels. Alternate clue giver and guesser. One-word clue plus count (1–3) is locked before guessing; correct tiles permit another guess until count exhausted or guesser ends turn. Neutral tile loses a life and swaps roles; trap ends match. Six targets within eight turns and three lives wins. Single-word clues cannot repeat a visible board word.

Both players ready a proposed game. Server validates every action and owns timers, secrets, turns and scoring. Actions bind to match, round and phase, preventing stale actions from altering a new turn. Temporary disconnect pauses Doodle's countdown; reconnect restores state and drawing. Persist active matches so server restarts recover them in paused state. Leaving an active match requires both partners' confirmation; abandoned matches do not count as wins.

## Records and deployment
Persist one completed match result atomically with final state; retries never double count. Personal wins/losses/draws are separate from joint wins/attempts, best scores and streaks. Retain recent history and per-game records. Single Node 24+ Fastify/Socket.IO process serves a Vite React/TypeScript build. SQLite uses local persistent storage with backups. Docker package runs as a non-root user. Production requires configured HTTPS origin, secure sessions, rate limits and origin checks. Cloud deployment is prepared, not performed without selecting the target.

The subsequent [UI and cat redesign](2026-10-01-ui-redesign.md) replaces the original copy, lobby layout and host presentation. Follow that spec for the current interface and roaming perspective cat.

## Verification
Meaningful engine tests for secrecy, equal turns, outcomes, invalid/stale actions, timeouts, pause/resume and clue turn rules. SQLite tests for session isolation, persistence, and idempotent records. HTTP and Socket.IO integration tests for unauthorized access and two-seat state. Playwright uses two independent phone browser contexts to complete all games, reconnect, check records and inspect layouts. Browser emulation cannot certify physical-phone battery, heat or Safari behavior; document that boundary.
